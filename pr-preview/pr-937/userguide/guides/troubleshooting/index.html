Troubleshooting¶

This page lists frequent messages of validate and frequent surprises of plan and apply, with their cause and how to address them. validate reports three levels of messages:

  • Error: the configuration cannot be applied, it must be fixed.
  • Warning: the configuration can be applied, but a setting will not be applied as specified.
  • Info: a remark, only shown with -v, e.g. a resource that will be skipped.

In the messages below, <repository> stands for the resource reported by validate, e.g. repository[name="my-repo"].

Values of the configuration¶

invalid value at '<path>': <value> is not of type '<type>'

A value does not have the type that otterdog expects, e.g. "0" instead of 0 for required_approving_review_count. Otterdog checks the configuration against its JSON schemas before any other validation, and stops at such an error. Other messages of the same form report a missing property, or a property that is not allowed at this place.

invalid value at '<path>': '<value>' is not one of [...]

The property only accepts the listed values, e.g. 'TITLE' instead of 'PR_TITLE' for merge_commit_title. The reference of the property lists the same values.

ignoring unknown properties found while validating organization config: Additional properties are not allowed ('<property>' was unexpected) (Warning)

The property is unknown to otterdog, usually because of a typo, e.g. has_wikki instead of has_wiki, and has no effect. Fix its name or remove it.

The Playground of the otterdog dashboard checks the same schemas while a configuration is edited: it underlines the invalid values and the unknown properties in the editor, and lists them when their number is clicked in its status. Its Validate button also has the configuration of an organization validated by otterdog, with limitations, see Validation in the Playground.

Code scanning¶

invalid value at '<path>.code_scanning_default_languages[<index>]': '<language>' is not one of [...]

The value is not a CodeQL identifier, e.g. java or kotlin instead of java-kotlin. Use one of the values listed in Supported languages.

<repository> has 'code_scanning_default_languages' configured while the repository does not yet exist.

Languages are checked against the languages detected in the repository, which requires the repository to exist. Create the repository first, with default setup enabled but without languages, then configure the languages in a second change, see Languages must be detected in the repository.

<repository> has 'code_scanning_default_languages' configured with '<language>' but this language is not detected in the repository. Detected languages: ...

GitHub does not detect any code of this language in the repository, e.g. python for a repository without Python code. Remove the language, or configure it once the code has been pushed. The detected languages are listed in the message.

Secrets and webhooks¶

<organization_codespaces|repository_codespaces> secrets of '<org>' are not available (GitHub answers 404 for '<path>'), they are skipped (Warning)

GitHub answers the Codespaces secrets endpoint with 404, e.g. because Codespaces is not available for the organization. Otterdog skips these secrets, other secrets are not affected. If the configuration declares Codespaces secrets, the operation fails instead with declares ... secrets which cannot be managed, as they cannot be compared with the live state: remove them, or make the endpoint available. To not read Codespaces secrets at all, use a default configuration without newOrgCodespacesSecret and newRepoCodespacesSecret.

<secret> only has a dummy value, resource will be skipped. (Info)
<webhook> has a secret set, but only a dummy secret '********' is provided in the configuration, will be skipped. (Info)

The value is redacted, usually after an import, as GitHub never discloses secret values. The resource is not changed by otterdog. Replace the value with a reference to a credential provider to manage it, see Secrets managed outside otterdog.

<secret> has a value '<value>' that does not use a credential provider. (Warning)

The value is written in the configuration, which is stored in a repository. Store it in a credential provider and reference it, see Reference secret values, never write them.

<secret> has 'visibility' of value 'private', which is not available for an organization with free plan.

Organizations on the free plan cannot restrict organization secrets and variables to private repositories. Use selected with the list of repositories instead.

Repositories¶

public <repository> has 'allow_forking' disabled which is not permitted. (Warning)

Public repositories can always be forked. Remove allow_forking: false from public repositories.

private <repository> has 'allow_forking' enabled, while the organization disables 'members_can_fork_private_repositories'.

The organization does not allow forking private repositories. Disable allow_forking for the repository, or allow forks in the settings of the organization.

private <repository> has 'has_wiki' enabled, which requires at least GitHub Team billing, currently using 'free' plan. (Warning)

Wikis of private repositories require a paid GitHub plan. Disable has_wiki for private repositories, see Enable only the features that are used.

<repository> has 'has_projects' enabled, while the organization disables 'has_organization_projects', setting will be ignored. (Warning)

Projects are disabled for the whole organization. Disable has_projects for the repository, or enable has_organization_projects for the organization.

<repository> has 'web_commit_signoff_required' disabled, while the organization requires it, setting will be ignored. (Warning)

The setting of the organization applies to all repositories, see Require a sign-off for commits made in the web interface. Remove the setting from the repository.

<repository> has defined an invalid topic '<topic>'. Only lower-case, numbers and '-' are allowed characters.

Topics follow the format of GitHub, e.g. github-actions instead of GitHub Actions, see Describe repositories.

<repository> has ('squash_merge_commit_title', 'squash_merge_commit_message') of value (...), while only combinations (...) are allowed.

GitHub only accepts some combinations of the title and the message of squash and merge commits, see Control the messages of merge and squash commits.

Rulesets and branch protection rules¶

<ruleset> has an invalid 'include_refs' pattern '<pattern>', while only values ('refs/heads/*', '~DEFAULT_BRANCH', '~ALL') are allowed

The branches of a ruleset are matched by their full ref, e.g. refs/heads/1.2.x rather than 1.2.x, or refs/heads/release/* for a pattern, see RefMatcher. The same applies to exclude_refs, and the tags of a ruleset with target: 'tag' start with refs/tags/.

use of organization rulesets requires an 'enterprise' plan, while this organization is currently on a '<plan>' plan.

Otterdog only accepts organization rulesets for organizations on the enterprise plan, although GitHub also provides them with GitHub Team. Use repository rulesets instead, see Organization-wide rulesets.

<ruleset> has 'enforcement' of value 'evaluate' which is only available for an 'enterprise' plan.

Use disabled to prepare a ruleset without enforcing it, see Prepare a ruleset before enforcing it.

<ruleset> has 'restricted_file_paths' set, while push rules are only supported by private and internal repositories.

GitHub rejects the push rules, e.g. restricted_file_paths or max_file_size, of a ruleset of a public repository when the ruleset is applied, whatever the plan of the organization. Push rulesets also require at least GitHub Team. Remove the push ruleset or make the repository private, see Restrict the files that can be pushed.

<ruleset> requires deployment environment '<environment>' which is not defined in the repository itself.

A ruleset or branch protection rule that requires a successful deployment can only reference an environment of the same repository. Define the environment in the repository, see Require a successful deployment before merging.

Plan and apply¶

plan shows changes that nobody made in the configuration

The configuration of the organization only contains the differences to its default configuration. A change of the default configuration, or a setting changed in the GitHub web interface, shows up in plan, see Inherited and explicit values.

A ruleset or branch protection rule created in the GitHub web interface is deleted

Otterdog manages all protections of the configured repositories, a protection that is not part of the configuration is removed when deletions are applied. Add it to the configuration instead, see the warning in Otterdog specifics.

A rotated secret is not updated on GitHub

Otterdog cannot detect that the value of a credential changed in the credential provider. Update the secret explicitly, see Updating secret values.

Changes to some organization settings are not applied automatically

Some settings, e.g. members_can_create_teams or the discussions of the organization, can only be changed through the GitHub web interface, which requires the credentials of a user that can log in to GitHub. plan and apply skip them with --no-web-ui, and such changes merged in a pull request of the configuration repository have to be applied manually, see Restrict what members can do.

Loading a page of the GitHub web interface times out

Settings that are only available through the GitHub web interface are retrieved with a headless browser, which waits up to 10 seconds for a page to load. On a slow connection this fails with an error like Page.goto: Timeout 10000ms exceeded. Increase the timeout, in milliseconds, with the environment variable OTTERDOG_WEB_TIMEOUT, e.g. export OTTERDOG_WEB_TIMEOUT=60000, or skip these settings with --no-web-ui, see Environment variables.

Validation in the Playground¶

The Validate button of the Playground of the otterdog dashboard has the configuration of an organization, created by orgs.newOrg(...), validated by otterdog on the server, with the default configuration of the Playground. It reports the messages of validate listed on this page, the infos included, at the property they are about, e.g. at the invalid value of include_refs, if it is set in the configuration, otherwise at the repository or the organization they are about. The evaluated configuration is only sent to the server when the button is clicked, it is neither stored nor applied.

The Propose on GitHub button of the Playground of a project validates the configuration the same way first. If otterdog finds errors, which would fail the validation of the pull request, or if the configuration cannot be validated, e.g. because of schema errors, it asks to confirm before proposing it.

A configuration without problem in the Playground can still be rejected by the validation of its pull request, or fail to be applied:

  • The validations depending on the organization on GitHub are skipped: the members of a team with skip_non_organization_members being members of the organization, and the languages of code_scanning_default_languages being detected in the repository, which must exist.
  • The checks only done when applying are not done, by validate neither: the teams, users and apps of bypass_actors must exist, and GitHub can reject a value that otterdog accepts.
  • The plan is not computed: whether the changes require secrets, settings only accessible via the GitHub web interface, or remove resources, which prevents their automatic merge, is only reported on the pull request. The Playground of a project shows the changes to the current configuration of the organization, though.
  • The configuration is not compared with the settings on GitHub, like /otterdog check-sync does on the pull request.
  • The default configuration is the one of the Playground: the global Playground validates with the default configuration it evaluates with, the one of the instance or the example of otterdog, which may not be the one of your organization. Use the Playground of your project to validate with its default configuration.
  • Only the configuration of an organization is validated: the button is not shown for a snippet, e.g. creating a repository, and is disabled for a configuration failing to evaluate or having schema errors, which otterdog does not validate further.
